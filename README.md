## 1. Лабораторийн зорилго

Энэхүү лабораторийн ажлаар Grafana k6 ашиглан веб системийн гүйцэтгэлийг ачааллын түвшин өөрчлөгдөх үед хэмжив. Үүнд latency, throughput болон error rate хэмжүүрүүдийг ашигласан. Мөн p90 болон p95 percentile утгуудыг харьцуулж, системийн гүйцэтгэлийн өөрчлөлтийг ажиглав. Threshold ашиглан SLO шаардлага хангасан эсэхийг шалгасан.

## 4. Суурь тест ба ачааллын түвшнүүд

5, 30 болон 100 VU түвшинд тус тусад нь 1 минутын тест ажиллуулж, p90, p95, throughput болон error rate хэмжүүрүүдийг харьцуулсан.

| VUs |       p90 |       p95 |       Throughput | Error rate |
| --: | --------: | --------: | ---------------: | ---------: |
|   5 | 265.57 ms | 313.93 ms |   6.920531 req/s |      0.00% |
|  30 | 268.69 ms | 274.61 ms |  43.194358 req/s |      0.00% |
| 100 | 277.86 ms | 295.42 ms | 141.410867 req/s |      0.00% |

### Үр дүнгийн ажиглалт

VU-ийн тоо 5-аас 100 хүртэл өсөхөд throughput 6.920531 req/s-ээс 141.410867 req/s хүртэл өссөн. Харин p90 болон p95 latency энэ ачааллын хүрээнд огцом өсөөгүй. 5 VU үед p95 нь 313.93 ms байсан бол 30 VU үед 274.61 ms, 100 VU үед 295.42 ms болсон. Бүх тестийн error rate 0.00% байсан. Иймээс энэ туршилтын хүрээнд test.k6.io сервер 100 VU хүртэл тогтвортой ажилласан гэж үзэж байна.

## 6. SLO тодорхойлсон нь

Суурь буюу 5 VU тестийн p95 latency:

```text
313.93 ms
```

SLO-г суурь p95 latency-ийн 1.5 дахин утгаар тодорхойлсон:

```text
313.93 × 1.5 = 470.895 ms ≈ 471 ms
```

Иймээс latency-ийн SLO:

```text
p95 < 471 ms
```

Error rate-ийн SLO:

```text
error rate < 1%
```

1.5 дахин нөөц сонгосон нь суурь гүйцэтгэлээс тодорхой хэмжээний хэлбэлзэл гарах боломжийг тооцож, хэт хатуу бус боловч хэмжигдэхүйц шаардлага тогтоох зорилготой.

## 7. Threshold test

### 7.1 Threshold PASS

Жинхэнэ SLO threshold:

```text
p(95) < 471 ms
rate < 0.01
```

PASS тестийн үр дүн:

| Threshold       | Бодит утга |  Үр дүн  |
| --------------- | ---------: | :------: |
| p95 < 471 ms    |  297.59 ms | **PASS** |
| Error rate < 1% |      0.00% | **PASS** |

### 7.2 Threshold FAIL

Threshold ажиллаж байгааг баталгаажуулахын тулд туршилтын үед latency threshold-ийг зориудаар маш бага утгаар тохируулсан.

```text
p(95) < 50 ms
```

Бодит p95:

```text
281.94 ms
```

Иймээс:

```text
281.94 ms > 50 ms
```

болж latency threshold **FAIL** болсон.

Error rate threshold:

```text
rate < 0.01
```

бөгөөд бодит error rate нь 0.00% байсан тул **PASS** болсон.

Энэ туршилтаар threshold нь шаардлага хангаагүй үед k6 тестийг FAIL төлөвт оруулж чаддаг болохыг баталгаажуулсан.

## 8. Дүгнэлт

Энэхүү лабораторийн ажлаар Grafana k6 ашиглан системийн гүйцэтгэлийг өөр өөр ачааллын түвшинд хэмжсэн. VU-ийн тоо 5-аас 100 болон өсөхөд throughput 6.920531 req/s-ээс 141.410867 req/s хүртэл нэмэгдсэн. p90 болон p95 latency нь туршилтын хүрээнд огцом өсөөгүй бөгөөд 100 VU үед p95 нь 295.42 ms байсан. Бүх үндсэн тестүүдэд error rate 0.00% гарсан. Энэ нь ачаалал нэмэгдэх үед throughput болон latency-г тусад нь ажиглах шаардлагатайг харуулсан. Мөн percentile хэмжүүрээр хэрэглэгчдийн ихэнх хүсэлтийн гүйцэтгэлийг үнэлж болохыг туршилтаар баталгаажуулсан. Суурь 5 VU тестийн p95 болох 313.93 ms утга дээр үндэслэн SLO-г p95 < 471 ms, error rate < 1% гэж тодорхойлсон. Threshold PASS тестээр 297.59 ms p95 болон 0.00% error rate гарч SLO шаардлагыг хангасан. Харин зориудаар p95 < 50 ms гэсэн хатуу threshold тохируулахад 281.94 ms гарч FAIL болсон нь threshold механизм зөв ажиллаж байгааг баталсан. Ингэснээр системийн гүйцэтгэлийг тоон үзүүлэлтээр үнэлэх, ачааллын өөрчлөлтийн нөлөөг ажиглах болон тодорхой гүйцэтгэлийн шаардлагыг threshold ашиглан шалгах практик туршлага олж авлаа.
